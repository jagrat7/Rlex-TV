3 What happens when you save a file

next devhot swap · state kept
  1. Savepage.tsx
  2. Dev serverrecompiles that module
  3. HMR pushsends it to the browser
  4. Fast Refreshswaps the component, keeps state
watchexec -r -e rs -- cargo runrestart · state reset
  1. Savesrc/ui/home.rs
  2. watchexecsees it, kills the running app
  3. cargorecompiles only the rlex crate; deps cached in target/
  4. Linkwrites target/debug/rlex
  5. Relaunchwindow reopens on Home; your data on disk is kept
No dev server: you always run a real compiled binary bacon run-long does the same kill-then-restart, with an error panel watchexec 2.8.0 is installed via mise

Sources: watchexec · bacon config (run-long uses on_change_strategy = "kill_then_restart") · Next.js Fast Refresh

4 Debug vs release

Debugcargo run
Compile time App speed Safety checks

≈ next dev. Default opt-level = 0, but Rlex builds GPUI, taffy, resvg and image at 3, so the UI stays smooth. Overflow checks and debug_assert! are on.

Releasecargo run --release
Compile time App speed Safety checks

≈ next build. opt-level = 3 everywhere; overflow checks and debug assertions off. Rlex also strips symbols.

Bars are relative, not measured.

Sources: Cargo profiles · Rlex Cargo.toml [profile.dev.package]

5 Cargo.toml ↔ package.json

Rlex's Cargo.toml (trimmed)
1[package]

2edition = "2024"
3[dependencies]

4tokio = { version = "1",

5[profile.release]

The package.json it would be
{
1 "name": "rlex",
"version": "0.1.0",
2 "type": "module",
3 "dependencies": {
"react": "19.0.0",
"lodash": "^4"
},
"scripts": {
"dev": "next dev",
"build": "next build"
}
}
1
IdentitySame fields, TOML instead of JSON.
2
EditionWhich Rust language rules apply. The loose Node match is "type": "module".
3
Versions"1" means ^1, like npm's caret. "=0.8.1" pins exactly.
4
FeaturesTurn on optional parts of a crate at compile time. npm has no equivalent.
5
ProfilesCompiler settings per build mode. Closest match: build options in next.config.js.
·
No scriptscargo's subcommands are fixed; add shortcuts with [alias].

6 Where the code runs

In Rlex the "frontend" and "backend" live in one process, so they talk through function calls instead of HTTP. Slow work is sent to Tokio with runtime::run, the UI thread awaits the result, and cx.notify() re-renders whatever views are watching. It's like a React state update. The one HTTP server in Rlex is the localhost torrent stream that mpv reads from.

Sources: src/runtime.rs · src/state.rs · Tokio tutorial · Node event loop

7 Rlex's modules as a Node project

The biggest difference is in the "State" row. state.rs plays the role of both the client store and the API layer. There's no network boundary between them, so there are no request or response types to keep in sync.

8 Your day-to-day on Rlex

While coding

watchexec -r -e rs -- cargo run
# or, with an error panel:
bacon run-long

Use debug builds: they rebuild faster, and the GPUI crates are already optimized.

Before committing / for real use

cargo fmt && cargo clippy && cargo test
cargo build --release
./target/release/rlex

≈ prettier && eslint && vitest, then next build.
